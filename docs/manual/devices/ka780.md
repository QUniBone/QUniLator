The **KA780** is the processor of a VAX-11/780. QUniLator runs it as a device of
its own: the processor, its memory and its console are inside the software, and
its UNIBUS adapter puts it on the UniBone's bus, where the emulated peripherals —
a UDA50 disk controller, a DEUNA, a serial multiplexer — answer it as they would a real 780's
adapter. It is listed as `cpuvax`, of type `VAX-11/780`.

> **UNIBUS · UniBone**
>
> An emulated processor is UNIBUS-only. A QBone drives a real CPU board and ships
> no processor emulation.

[VMS on an emulated VAX-11/780](../walkthroughs/vax-vms.md) builds a whole machine
around it, step by step.

## What the machine sees

| | |
|---|---|
| **Processor** | A VAX-11/780. With VMS idle at its prompt it executes about five times as many instructions a second as the original |
| **Memory** | 1, 2 or 4 MB, set by `memory` |
| **Console** | The processor's own console terminal, on the console channel `/ws/console/vax`. The dashboard's terminal connects to it on its own |
| **UNIBUS** | One UNIBUS adapter. The I/O page and a device's transfers through the map registers go out on the bus |
| **Boot** | START boots `bootdevice`: `RQ0`, drive 0 of the UDA50 at 772150, unless set otherwise. See [Booting](#booting) |
| **Clock** | Advances with the instructions executed, at the 2 µs an instruction a real 780 takes |

There is no time-of-year clock behind it, so VMS asks for the date and time on
every boot.

## Using it

1. Add `cpuvax` on the **Configurations** screen with the peripherals the machine
   needs: at least a `uda` with a drive holding a system disk.
2. Set **External console** to **Off** on the **Machine** screen. The VAX talks on
   its own console, not on the cape's serial port.
3. Enabling the processor builds the machine and leaves it halted. **START** on
   the dashboard boots it.

`memory`, `bootimage`, `bootdevice`, `bus_iopage` and `bus_exclusive` are read
when the processor is enabled. To change one, disable the processor, change it,
and enable it again.

## Where the devices are

Everything on this page that says *the bus* means the **UNIBUS**, the one the
UniBone is plugged into. In a backplane it is the real one, with real cards on
it; on a card running on its internal bus, it is the card's own copy of those
signals. Either way it is a single bus, and the emulated devices — `uda`,
`deuna`, `dzv11` and the rest — are cards on it. They answer the VAX at their
UNIBUS addresses exactly as a real card in that slot would, and a real card on
the backplane is reached the same way. There is no second, simulated bus.

The processor reaches that bus through its UNIBUS adapter, as a real 780 does
through its DW780. Inside the VAX emulation there is one more MSCP controller,
which never appears on the UNIBUS: a test fixture for running the processor
with no devices configured, used only when `bootimage` names a disk image. A
working machine leaves `bootimage` empty and does not use it.

## Booting

START boots what `bootdevice` names. It is the argument a 780 console's `BOOT`
command takes, spelled the way SIMH spells it:

| `bootdevice` | Boots |
|---|---|
| `RQ0` *(the default)* | drive 0 of the UDA50 at 772150, the `uda` drive whose `unit` is 0 |
| `RQ1`, `RQ2`, `RQ3` | drive 1, 2 or 3 of the same UDA50 |
| `RQ0 /R5:1` | drive 0, with boot flags 1 in R5: a conversational boot, which stops VMS at `SYSBOOT>` |
| `CS` | the console floppy, the floppy `image` names |
| *empty* | nothing. START resets the processor, which halts again at once |

The boot flags are the value VMB finds in R5, in hex, as SIMH and the 780
console both take them: `/R5:10` is 10 hex, 16 decimal. `RQ0/R5:1` and
`RQ0 /R5:1` are the same command. Two values VMS defines:

| R5 | Effect |
|---|---|
| `1` | conversational boot: `SYSBOOT>` comes up before the system starts, for `SET` and `SHOW` on the system parameters; `CONTINUE` boots on |
| `10000000` | boot from root `[SYS1]` in place of `[SYS0]` — the top digit is the root number |

The VMS installation guide for the version on the disk lists the rest.

## The console

The console terminal on `/ws/console/vax` is VMS's `OPA0:` — what the operating
system prints and reads. The 780's console subsystem, the LSI-11 with its `>>>`
prompt, is not there, so a halted processor prints nothing on it and no console
command can be typed. What those commands did is done with the processor's
parameters and the dashboard:

| 780 console | QUniLator |
|---|---|
| boot from `DUA1` | `bootdevice` = `RQ1`, then **START** |
| boot from `DUA0` with R5 = 1 | `bootdevice` = `RQ0 /R5:1`, then **START** |
| `HALT` | **HALT**, or `halt_switch` = 1 |
| `CONTINUE` | **CONT**, or `continue_switch` = 1 |
| `EXAMINE`, `DEPOSIT` on memory | `mem_examine`, `mem_deposit`, `mem_data` |
| `EXAMINE`, `DEPOSIT` on a UNIBUS register | `bus_examine`, `bus_deposit`, `bus_data` |

`bus_examine`, `bus_deposit` and `bus_data` are those two commands on the I/O
page and nothing more. They play no part in booting.

## The console floppy

A 780's console carries an RX01 drive of its own, which VMS calls `CSA1:`. It
is part of the processor, separate from any RX11 or RX211 on the UNIBUS, and
`image` names the floppy in it: an RX01 image of 256256 bytes, in the drive's
physical sector order. The KA780 card on the dashboard shows it beside **CSA1**,
and a click there opens the image library.

The floppy changes at any time, as on the real drive, so a multi-volume kit is
fed one floppy after another while the machine runs. What the machine writes
reaches the file within a few seconds, and when the floppy comes out. An RX01
has no write protection: a file protected in the image library (mode 444) goes
in as any other floppy, and what the machine writes to it is dropped when it
comes out.

VMS reaches the drive once it has been connected, and mounts a Files-11 floppy
in it as it would any disk:

```
$ MCR SYSGEN
SYSGEN> CONNECT CONSOLE
SYSGEN> EXIT
$ MOUNT CSA1: label
```

`bootdevice` = `CS` and **START** boot from the floppy. VMB loads the boot file
across as many volumes as the kit has, asking on the console for each one, and
a standalone BACKUP kit runs this way. The boot hands VMS unit 1, the unit of
`CSA1:`, which its console floppy driver addresses on every transfer.

## Empty, 0, and not set

A text parameter such as `bootdevice` or `bootimage` can be *empty*, which is a
value of its own: an empty `bootdevice` boots nothing. A number or a switch is
never empty; 0 is its value.

A parameter a configuration does not name takes its default. A saved
configuration lists only what differs from the defaults, so one that names no
`bootdevice` boots `RQ0`, and one that should boot nothing stores
`"bootdevice": ""`. The defaults are in the table under [Parameters](#parameters).

## Example configurations

A configuration is a JSON file in `/var/lib/qunilator/configs/` on the board,
written by **Save** on the **Configurations** screen. The examples carry
comments for reading; the files themselves have none. Image paths are relative
to `/var/lib/qunilator`.

### VMS from drive 0

The usual machine, and the one [VMS on an emulated VAX-11/780](../walkthroughs/vax-vms.md)
builds. Nothing on `cpuvax` is changed from its default, so it boots `RQ0`.

```jsonc
{
  "title": "VAX-11/780 with VAX/VMS V4.7",
  "devices": [
    // the UDA50 at 772150: the disk controller RQ names
    {"name": "uda", "enabled": true, "params": {}},
    // its drive with unit 0, which is RQ0 to the boot command and DUA0: to VMS
    {"name": "uda0", "enabled": true, "params": {"image": "images/vms47.dsk"}},
    // Ethernet, on the board's interface veth-pdp
    {"name": "deuna", "enabled": true, "params": {"interface": "veth-pdp"}},
    // the processor: 4 MB, and bootdevice left at its default RQ0
    {"name": "cpuvax", "enabled": true, "params": {"memory": "4"}}
  ]
}
```

### Two disks, booting the second

The system disk on drive 1, a data disk on drive 0. VMS comes up with
`SYS$SYSDEVICE` on `DUA1:`.

```jsonc
{
  "title": "VAX-11/780 booting DUA1",
  "devices": [
    {"name": "uda", "enabled": true, "params": {}},
    // drive 0: a data disk VMS mounts after it is up
    {"name": "uda0", "enabled": true, "params": {"image": "images/data.dsk"}},
    // drive 1: the system disk
    {"name": "uda1", "enabled": true, "params": {"image": "images/vms47.dsk"}},
    // RQ1 is the drive whose unit is 1, which uda1 has by default
    {"name": "cpuvax", "enabled": true, "params": {"memory": "4", "bootdevice": "RQ1"}}
  ]
}
```

### A conversational boot, once

Boot flags are usually wanted for one boot, to change a system parameter, so
they are set on the running machine and not saved. In the web interface:

1. On the **Configurations** screen, the current configuration is the running
   machine. Open **Parameters** on the **KA780 processor** row and set
   `bootdevice` to `RQ0 /R5:1`. The change reaches the machine at once, and the
   configuration shows **MODIFIED**.
2. Press **START** on the KA780 card of the **Dashboard**. START stops whatever
   the processor runs and boots afresh, and the console stops at `SYSBOOT>`.
3. Set the system parameters at `SYSBOOT>`; `CONTINUE` boots on.

The next boot is an ordinary one once `bootdevice` is `RQ0` again: set it back
the same way, or press **Revert** on the configuration, which puts back the
saved machine and with it the default `RQ0`. Revert leaves the machine
switched off, and [AUX ON/OFF](../operating/dashboard.md#control-panel) brings
it up again.

The same steps can be scripted against the board's
[web API](https://github.com/QUniBone/QUniLator/blob/main/10.05_web/docs/api.md),
from a shell on any computer that reaches the board. Each parameter is a `PUT`
of a JSON value, under the device name `cpuvax`, with the web login:

```sh
BOARD=unibone                          # the board's host name
AUTH="operator:password"               # the web interface's login

curl -s -u "$AUTH" -X PUT -H 'Content-Type: application/json' \
     -d '{"value": "RQ0 /R5:1"}' http://$BOARD/api/devices/cpuvax/params/bootdevice
curl -s -u "$AUTH" -X PUT -H 'Content-Type: application/json' \
     -d '{"value": "1"}' http://$BOARD/api/devices/cpuvax/params/start_switch
```

## What has been verified

- VMS V4.7 boots from the emulated UDA50 to a login prompt. The project's
  hardware test runs that boot on a UniBone every night and before each release.
- DEC's processor diagnostics EVKAA, EVKAB, EVKAC and EVKAD pass on the
  emulation core.
- Under VMS V4.7 the console floppy is connected, initialised, mounted, written
  and read back: a file copied to it compares equal to its original, and the
  image read off the board decodes as the same Files-11 volume.
- A VMS V5.3 standalone BACKUP kit for the 780 boots from the console floppy:
  START with `bootdevice` = `CS`, then each volume (SYSTEM_1 to SYSTEM_4, then
  BACKUP) put in through `image` when the console asks for it. Standalone BACKUP
  comes up at its `$` prompt.

### In detail

#### `memory`

The memory the processor has, in megabytes: 1, 2 or 4. The board shares 4 MB with the bus, and the processor's memory has to fit in it so that a device's transfer can reach it, so 4 is the most a board can give. The size is read when the processor is enabled; changing it means disabling the processor first.

#### `bootimage`, `bootdevice`

What START boots. `bootdevice` is the argument of a 780 console's BOOT command, in SIMH's spelling: a drive of the UDA50 at 772150, `RQ0` to `RQ3` for the `uda` drive whose `unit` is 0 to 3 — `uda0` to `uda3` unless a unit was changed — or a drive of the RK611 at 777440, `HK0` to `HK7` for the `hk` drive with that unit, from which VMB loads the system over the bus. Boot flags follow as `/R5:` and a hex value, so `RQ0 /R5:1` stops VMS at `SYSBOOT>` for a conversational boot; with none, R5 is 0. An empty `bootdevice` boots nothing: START resets the processor and it halts again at once. A change takes effect at the next START, so the boot flags for one boot are set on the running machine and START pressed.

`bootimage` stays empty on a working machine: the disks are the `uda` drives, cards on the UNIBUS like any other. A file named here is instead attached to a test MSCP controller that is part of the VAX emulation itself and never appears on the UNIBUS. It answers at the same 772150, so `bus_exclusive` has to be 0 for it, and it boots whatever `bootdevice` names. It is there for testing the processor with no devices configured; enabling the processor fails when it names no disk image file or an empty one.

`bootimage` is read when the processor is enabled.

#### `image`

The console floppy: the RX01 drive that is part of a 780's console, which VMS calls `CSA1:` once `SYSGEN CONNECT CONSOLE` has made it known. `image` names the RX01 image in it, 256256 bytes, and empty leaves the drive empty. It is the processor's own drive, separate from the RX11 or RX211 on the UNIBUS, which VMS calls `DY` or `DX`.

`bootdevice` set to `CS` boots from it, which is how a 780 starts standalone BACKUP.

The floppy can be changed at any time, as on the real drive. What the machine writes reaches the file within a few seconds, and when the floppy is changed or the processor disabled. An RX01 has no write protection, so a protected file (mode 444) goes in as any other floppy and keeps none of what is written to it.

#### `core_debug`, `core_history`

Debugging aids for the emulation itself. `core_debug` names a device the processor carries inside it, such as `RQ`, and writes the core's own trace of it to `/tmp/simh-<device>.log` on the board. `core_history` keeps that many of the last instructions executed and writes them to `/tmp/vax-history.log` after an interrupt arrives from the bus; it can only be changed while the processor is halted.

#### `bus_iopage`, `bus_dma`, `bus_exclusive`

How the processor's UNIBUS adapter meets the bus. All three are on for a working machine, and are there to take the bus out of the picture when comparing against the emulation alone.

`bus_iopage`: the processor's accesses to the I/O page become bus cycles and reach the devices on the bus. Off, the machine sees only the devices the processor carries inside it.

`bus_dma`: a device's transfer to or from memory goes out on the bus and is translated through the adapter's map registers there, as on a real UNIBUS, so a card that is not emulated can take part. Off, the transfer is answered inside the program.

`bus_exclusive`: the bus answers the whole I/O page, including the addresses of the controllers the processor carries inside it. Off, it answers only the addresses those leave free.

`bus_iopage` and `bus_exclusive` are read when the processor is enabled.

#### `bus_examine`, `bus_deposit`, `bus_data`

What a real 780's console does with EXAMINE and DEPOSIT on a UNIBUS register, and a way to reach a device before an operating system has a driver for it. Writing an address (octal, as a UNIBUS address) to `bus_examine` reads that register and leaves the word in `bus_data`. To write one, set `bus_data` first, then write the address to `bus_deposit`. Every write makes the access, the same address again included, so a register can be read repeatedly. The access is made by the processor, so it needs the processor enabled; applying a configuration makes none.

#### `mem_examine`, `mem_deposit`, `mem_data`

The other half of what a 780's console reaches: the processor's own memory, by physical address, in hex. Writing an address to `mem_examine` leaves the longword there in `mem_data`; to change it, set `mem_data` and write the address to `mem_deposit`. As on the bus, every write makes the access.

#### `bus_cycles`, `bus_timeouts`, `bus_interrupts`, `dma_words`, `dma_failures`

What the UNIBUS adapter has carried since the processor was enabled: register accesses, those nothing answered, and interrupts taken from devices. `bus_timeouts` rising during a boot is normal: the operating system probes addresses to find out which devices are there.

`dma_words` counts the words devices moved through the map registers (a byte written counts as one), and `dma_failures` the transfers the map refused because no valid map register covers the page — on a real adapter, a device writing where the operating system has not mapped anything. All of them start again from 0 when the processor is enabled.

#### `dma_byte_offset`

A map entry with the byte offset bit set moves the transfer one byte up, so the processor's address is odd where the device's is even. This counts the transfers that took that path, which is the one a driver's unaligned buffer takes.

#### `batch`

How many instructions the processor runs before it looks at the switches and the power state again. The default is long enough that the check costs nothing and short enough that a HALT takes effect at once.

#### `emulated_time`

The machine's clock advances with the instructions it executes, at the 2 µs an instruction a real 780 takes, so the interval timer and every device delay keep pace with the processor whatever else the board is doing. VMS calibrates its timing loops once at boot; on the wall clock, a boot the board's other work interrupts during that moment mis-times every driver wait from then on. Set to 0, the clock follows the wall, which is there to compare against real-time behaviour.

#### `run_led`, `halt_switch`, `start_switch`, `continue_switch`

The processor's front panel, which the dashboard's RUN, HALT, START and CONT controls drive. `start_switch` and `continue_switch` act once and fall back to 0. Enabling the processor builds the machine and leaves it halted; START boots it from `bootdevice`.

#### `PC`, `PSL`, `IPL`, `uba_init`, `iopage_dispatches`, `iopage_claimed`

Where the processor is, read whenever it stops and as it runs: the program counter, the processor status longword and the interrupt priority level it runs at, all in hex. `uba_init`, `iopage_dispatches` and `iopage_claimed` describe the UNIBUS adapter: whether it is being initialised, how many I/O page accesses the processor has made, and how many words of the I/O page the bus answers (4096 is all of it).

#### `iopage_reclaims`, `bootdev_on_bus`

A reset of a controller the processor carries inside it takes the boot device's registers back from the bus. They are handed back to the bus at once; this counts how often that happened, and `bootdev_on_bus` says whether the bus has them now.

#### `uba_cr`, `intr_pending`, `uba_dr`, `nexus_req`, `intr_vector_cell`, `intr_vector_stored`, `intr_level_stored`

The UNIBUS adapter's registers and interrupt state, for diagnosing a machine that is not taking a device's interrupts. `intr_pending` is the bus request level whose vector the adapter is still holding; non-zero for long says the processor is not taking what it was given. `nexus_req` shows the requests BR4 to BR7 the adapter has posted and the processor has not yet taken.

#### `iotrace_dump`

Writes the processor's last 64 accesses to the boot device's registers, and the interrupts between them, to the log, together with the instruction history when `core_history` is on. It acts once and falls back to 0.
