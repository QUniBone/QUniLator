The **KA780** is the processor of a VAX-11/780. QUniLator runs it as a device of
its own: the processor, its memory and its console are inside the software, and
its UNIBUS adapter puts it on the UniBone's bus, where the emulated peripherals —
a UDA50 disk controller, a DEUNA, a serial multiplexer — answer it as they would a real 780's
adapter. It is listed as `cpuvax`, of type `VAX-11/780`.

> **UNIBUS · UniBone**
>
> An emulated processor is UNIBUS-only. A QBone drives a real CPU board and ships
> no processor emulation.

[VMS on an emulated VAX-11/780](../walkthroughs/vax-vms.md) builds a whole machine
around it, step by step.

## What the machine sees

| | |
|---|---|
| **Processor** | A VAX-11/780. With VMS idle at its prompt it executes about five times as many instructions a second as the original |
| **Memory** | 1, 2 or 4 MB, set by `memory` |
| **Console** | The processor's own console terminal, on the console channel `/ws/console/vax`. The dashboard's terminal connects to it on its own |
| **UNIBUS** | One UNIBUS adapter. The I/O page and a device's transfers through the map registers go out on the bus |
| **Boot** | The console boots `bootdevice` — `RQ0`, drive 0 of the UDA50 at 772150, unless set otherwise |
| **Clock** | Advances with the instructions executed, at the 2 µs an instruction a real 780 takes |

There is no time-of-year clock behind it, so VMS asks for the date and time on
every boot.

## Using it

1. Add `cpuvax` on the **Configurations** screen with the peripherals the machine
   needs: at least a `uda` with a drive holding a system disk.
2. Set **External console** to **Off** on the **Machine** screen. The VAX talks on
   its own console, not on the cape's serial port.
3. Enabling the processor builds the machine and leaves it halted. **START** on
   the dashboard boots it.

`memory`, `bootimage`, `bootdevice`, `bus_iopage` and `bus_exclusive` are read
when the processor is enabled. To change one, disable the processor, change it,
and enable it again.

## What has been verified

- VMS V4.7 boots from the emulated UDA50 to a login prompt. The project's
  hardware test runs that boot on a UniBone every night and before each release.
- DEC's processor diagnostics EVKAA, EVKAB, EVKAC and EVKAD pass on the
  emulation core.

### In detail

#### `memory`

The memory the processor has, in megabytes: 1, 2 or 4. The board shares 4 MB with the bus, and the processor's memory has to fit in it so that a device's transfer can reach it, so 4 is the most a board can give. The size is read when the processor is enabled; changing it means disabling the processor first.

#### `bootimage`, `bootdevice`

The disk the machine boots from, and where it is. With `bootimage` empty — the usual machine — every peripheral is a device on the bus, and `bootdevice` names the unit the console boots: `RQ0` is drive 0 of the UDA50 at 772150, which is where the emulated `uda` answers. With an image named in `bootimage`, it is attached to an MSCP controller inside the processor instead, at the same address; `bus_exclusive` then has to be 0, so the bus leaves that address to it. This is for bringing a machine up before its devices are configured. An empty `bootdevice` brings the processor up at its console prompt without booting anything. Both are read when the processor is enabled.

#### `core_debug`, `core_history`

Debugging aids for the emulation itself. `core_debug` names a device the processor carries inside it, such as `RQ`, and writes the core's own trace of it to `/tmp/simh-<device>.log` on the board. `core_history` keeps that many of the last instructions executed and writes them to `/tmp/vax-history.log` after an interrupt arrives from the bus; it can only be changed while the processor is halted.

#### `bus_iopage`, `bus_dma`, `bus_exclusive`

How the processor's UNIBUS adapter meets the bus. All three are on for a working machine, and are there to take the bus out of the picture when comparing against the emulation alone.

`bus_iopage`: the processor's accesses to the I/O page become bus cycles and reach the devices on the bus. Off, the machine sees only the devices the processor carries inside it.

`bus_dma`: a device's transfer to or from memory goes out on the bus and is translated through the adapter's map registers there, as on a real UNIBUS, so a card that is not emulated can take part. Off, the transfer is answered inside the program.

`bus_exclusive`: the bus answers the whole I/O page, including the addresses of the controllers the processor carries inside it. Off, it answers only the addresses those leave free.

`bus_iopage` and `bus_exclusive` are read when the processor is enabled.

#### `bus_examine`, `bus_deposit`, `bus_data`

What a real 780's console does with EXAMINE and DEPOSIT on a UNIBUS register, and a way to reach a device before an operating system has a driver for it. Writing an address (octal, as a UNIBUS address) to `bus_examine` reads that register and leaves the word in `bus_data`. To write one, set `bus_data` first, then write the address to `bus_deposit`. The access is made by the processor, so it needs the processor enabled.

#### `mem_examine`, `mem_deposit`, `mem_data`

The other half of what a 780's console reaches: the processor's own memory, by physical address, in hex. Writing an address to `mem_examine` leaves the longword there in `mem_data`; to change it, set `mem_data` and write the address to `mem_deposit`.

#### `bus_cycles`, `bus_timeouts`, `bus_interrupts`, `dma_words`, `dma_failures`

What the UNIBUS adapter has carried since the processor was enabled: register accesses, those nothing answered, and interrupts taken from devices. `bus_timeouts` rising during a boot is normal: the operating system probes addresses to find out which devices are there.

`dma_words` counts the words devices moved through the map registers (a byte written counts as one), and `dma_failures` the transfers the map refused because no valid map register covers the page — on a real adapter, a device writing where the operating system has not mapped anything. All of them start again from 0 when the processor is enabled.

#### `dma_byte_offset`

A map entry with the byte offset bit set moves the transfer one byte up, so the processor's address is odd where the device's is even. This counts the transfers that took that path, which is the one a driver's unaligned buffer takes.

#### `batch`

How many instructions the processor runs before it looks at the switches and the power state again. The default is long enough that the check costs nothing and short enough that a HALT takes effect at once.

#### `emulated_time`

The machine's clock advances with the instructions it executes, at the 2 µs an instruction a real 780 takes, so the interval timer and every device delay keep pace with the processor whatever else the board is doing. VMS calibrates its timing loops once at boot; on the wall clock, a boot the board's other work interrupts during that moment mis-times every driver wait from then on. Set to 0, the clock follows the wall, which is there to compare against real-time behaviour.

#### `run_led`, `halt_switch`, `start_switch`, `continue_switch`

The processor's front panel, which the dashboard's RUN, HALT, START and CONT controls drive. `start_switch` and `continue_switch` act once and fall back to 0. Enabling the processor builds the machine and leaves it halted; START boots it from `bootdevice`.

#### `PC`, `PSL`, `IPL`, `uba_init`, `iopage_dispatches`, `iopage_claimed`

Where the processor is, read whenever it stops and as it runs: the program counter, the processor status longword and the interrupt priority level it runs at, all in hex. `uba_init`, `iopage_dispatches` and `iopage_claimed` describe the UNIBUS adapter: whether it is being initialised, how many I/O page accesses the processor has made, and how many words of the I/O page the bus answers (4096 is all of it).

#### `iopage_reclaims`, `bootdev_on_bus`

A reset of a controller the processor carries inside it takes the boot device's registers back from the bus. They are handed back to the bus at once; this counts how often that happened, and `bootdev_on_bus` says whether the bus has them now.

#### `uba_cr`, `intr_pending`, `uba_dr`, `nexus_req`, `intr_vector_cell`, `intr_vector_stored`, `intr_level_stored`

The UNIBUS adapter's registers and interrupt state, for diagnosing a machine that is not taking a device's interrupts. `intr_pending` is the bus request level whose vector the adapter is still holding; non-zero for long says the processor is not taking what it was given. `nexus_req` shows the requests BR4 to BR7 the adapter has posted and the processor has not yet taken.

#### `iotrace_dump`

Writes the processor's last 64 accesses to the boot device's registers, and the interrupts between them, to the log, together with the instruction history when `core_history` is on. It acts once and falls back to 0.
